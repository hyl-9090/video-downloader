# 视频下载器 · 更新日志

> 一个给老师用的视频下载小工具：把链接粘进来 → 选清晰度 → 下载。
> 底层用 yt-dlp，**实测**支持 B站 / 抖音 / 小红书 / 微博 / 腾讯视频 / 优酷 / 爱奇艺 / 芒果TV / 西瓜视频 / 斗鱼 / 虎牙 / 喜马拉雅 / 网易云音乐 等 **1700 多个**网站。
> ⚠️ **微信视频号、快手、微视、咪咕视频、皮皮虾不支持**（下载引擎没有这几个平台的提取器）。
> 在鸿蒙电脑和 Windows 上都能跑；Windows 版可打包成单个 exe，双击即用。

- **当前版本**：界面 v1.5（源码 `downloader/launcher/`）
- **已交付产物**：`视频下载器.exe`（17,589,901 字节，x64）
- **维护人**：小创（东莞虎门外语学校）

## v1.5 — 平台支持度查清 + 不支持的提前拦下

**背景**：用户问「微信视频号能不能下」。查了才知道——**不能**，而且顺带发现旧版界面里的平台支持表**是错的**（把快手写成了支持）。

### 实测：yt-dlp 2026.08.19 提取器全表核查（共 1751 个提取器）

| 平台 | 结论 |
|---|---|
| B站（含番剧/直播/合集/收藏夹） | ✅ 支持 |
| 抖音 | ✅ 支持（含无水印） |
| 小红书 | ✅ 支持 |
| 微博（weibo.com/数字/… 、/tv/show/… 、m.weibo.cn/status/…） | ✅ 支持 |
| 腾讯视频 / 优酷 / 爱奇艺 / 芒果TV | ✅ 支持 |
| 西瓜视频 / AcFun / 搜狐视频 | ✅ 支持 |
| 斗鱼 / 虎牙 | ✅ 支持 |
| 喜马拉雅 / 网易云音乐 / QQ音乐 / 酷我 | 🟡 看情况（音乐平台多需登录/会员；**酷我只认 `kuwo.cn/yinyue/<数字>`**，网页上复制的 `/play_detail/` 认不出） |
| **微信视频号（含公众号视频）** | ❌ **无提取器，下不了** |
| **快手** | ❌ **无提取器，下不了** |
| 微视 / 咪咕视频 / 皮皮虾 | ❌ 无提取器 |

> 微信视频号下不了的根本原因：微信的视频是**加密的、必须登录微信客户端才能播放**，
> 属于封闭生态，公开的下载工具（不只是本工具）都拿不到。

### 新增
- **平台支持表改准确版**：加「能不能下」一列，用 ✅ 能 / ❌ 不行 / 🟡 看情况 明确标注，
  并注明**这是实测结果、不是估计的**。
- **不支持的平台提前拦下**：命中视频号 / 快手 / 微视 / 咪咕 / 皮皮虾等域名时，
  解析前直接返回**中文说明 + 替代办法**（请作者发原视频 / 用手机录屏），
  不再让用户对着 `Unsupported URL` 的英文报错猜。
- 解析到页面但**没找到可下格式**时（如 YouTube 近年加强限制的情况），页面会给出明确提示，
  而不是显示一张空列表。

### 变更
- YouTube 从「✅ 能」改为「🟡 看情况」：需要能正常访问，且近年 YouTube 加强了限制，
  部分视频解析不到，以实测为准。
- 《使用说明》里的示例平台去掉了快手（避免误导）。

### 最终验收（v1.5 收尾，逐项实跑）

| # | 项目 | 方法 | 结果 |
|---|---|---|---|
| A1 | `launch.py` 语法 | `py_compile` | ✅ |
| A2 | 界面 JS 语法 | 抽出 `<script>` 跑 `node --check` | ✅ |
| A3 | DOM 引用完整性 | 比对 HTML 的 id 与 JS 的 `$("#…")` | ✅ 无缺失 |
| A4 | 关键函数存在性 | 检查 6 个新函数是否真在代码里 | ✅ 全部存在 |
| B1 | 服务接口 | `/health`、`/status`、`/` 均探活 | ✅ 全 HTTP 200 |
| B2 | 依赖状态 | `/status` 读 `ready` 与 notes | ✅ `ready=true`，备注正常 |
| C1 | 平台路由核对 | 用 20 条样例链接过 `extractor.suitable()` | ✅ B站/抖音/小红书/微博/腾讯/优酷/爱奇艺/芒果/西瓜/AcFun/搜狐/斗鱼/虎牙/喜马拉雅/网易云/QQ音乐/YouTube 有专属提取器；❌ 视频号/快手 无 |
| D1 | **真下载** | B站 360P 走「视频流+音频流→自动合并」 | ✅ 产出合法 MP4 **14,698,827 字节**（与预估一致、两次结果一字节不差） |

**验收过程中自己发现并纠正的 2 个问题**：
1. 首轮平台核对用了 `extractor.suitable()` 却**没排除 `Generic` 提取器**——它认领任何网址，
   导致出现「20/20 全部支持」的**假阳性**。排除 `Generic` 后才得到真实结果。
2. 「微博」「酷我」一开始被判 ❌，实为**我的样例网址不符合其真实格式**。
   调出 `_VALID_URL` 后用正确形式复测：微博 ✅（三种形式）、酷我 ✅（但**只认 `/yinyue/` 形式**）。

**⚠️ 验收边界（如实说明）**：C1 只验证到「**提取器存在 + 网址格式匹配**」这一层，
除 B站外**没有对每个平台做真实下载**（那需要各平台的真实链接，且多数要登录）。
因此实际能不能下，仍以你手上那条链接的实测结果为准。

## v1.4 — cookie 说清楚 + 自动转换

**背景**：老师普遍不知道「cookie」是什么；而且实测发现原来推荐的复制方式**根本无效**。

### 新增
- 界面「高级」板块重写为**两种 cookie 获取方法**：
  - **方法一（推荐）**：浏览器 `F12` → 网络/Network → 刷新 → 请求标头里的 `Cookie:` 那一行，整串复制。
  - **方法二**：装「Get cookies.txt LOCALLY」扩展 → 导出 `cookies.txt` → 全选复制。
- 🔐 安全提醒：cookie 等于登录凭证，**不要发给别人**；本程序只在本机用一次，用完即删、不上传。
- 常见问题新增 3 条：填了 cookie 还是 480P 怎么排查 / 为什么填了反而变低 / cookie 有没有风险。

### 修复
- 🔴 **`normalize_cookie()`：cookie 格式自动转换**。
  实测 yt-dlp **只认严格的 Netscape 格式**（且必须有 `# Netscape HTTP Cookie File` 头行），而 F12 复制的那串 `SESSDATA=…; bili_jct=…` 会被直接拒绝。
  现在两种格式都认：是 Netscape 就补头行；是 `k=v; k=v`（含 `Cookie: ` 前缀）就自动转成 Netscape，域名从视频链接自动推断。
- 🔴 **cookie 无效时自动降级重试**：带着坏 cookie 会让**整个解析**失败，现在会自动丢掉 cookie 再试一次，
  成功后页面弹橙色提示告知「cookie 无效已忽略」。

### 实测发现（重要）
无效 / 过期的 cookie **比不填更差**（可复现）：

```
不带 cookie    →  1080P / 720P / 480P / 360P / 仅音频
带伪造 cookie  →  480P / 360P / 仅音频        ← 画质反而变少
```

网站认不出你是会员时，会直接按「未登录」处理。所以：**不需要就别填**。

## v1.3 — 让不懂技术的人也能用

**背景**：使用者是不懂技术的老师，原本文案里「Netscape 格式」「cookie」这类词看不懂，报错也是英文。

### 新增
- 页面底部《📖 使用说明》：三步图文流程 + **《各平台怎么复制链接》表格**
  （B站 / 抖音 / 快手 / 小红书 / 微博 / 微信视频号 / YouTube / 腾讯爱奇艺优酷 / 其它）。
- 输入框下方「三步搞定」流程条 + 一键跳到说明。
- **分享文案自动识别**：抖音等 App 复制出来的是一整段带汉字的文案，
  现在直接整段粘就行，程序会自动把链接抠出来；也支持只粘 B站 **BV 号 / av 号**。
- **报错说人话**：把 yt-dlp 的英文报错按情况翻译成
  「链接不支持 / 连不上网站 / 需要登录 / 视频已删除」四种提示，原始报错折进「技术详情」。

### 变更
- **cookie 从主表单降级**到折叠的「高级」里 —— 老师默认看到的界面不再有这一项，
  并明确写着「不知道是什么就留空即可」。

## v1.2 — 修两个最烦人的体验问题

### 修复
- 🔴 **ffmpeg 每次运行都重下 50MB**。
  原因：onefile 打包的 exe，运行时解压目录是**临时的**，而旧代码把 ffmpeg 存在那里。
  现在改存到**持久目录**（`%LOCALAPPDATA%\VideoDownloader\bin`），**只下一次**。
- 🔴 **首次双击像假死**。
  原因：启动时同步等依赖准备好才开界面，第一次要下 50MB，界面迟迟不出来。
  现在改成**先开界面、依赖后台下载**，页面顶部显示进度；下载完成后提示会自动消失。
- 多源下载 ffmpeg（gyan.dev 慢就换备用源），并**先写 `.part` 再落盘**，避免半成品被当成好的。
- 给 yt-dlp 加**下载重试**（`retries=10 / fragment_retries=10 / socket_timeout=30`）。
  实测触发过 B站 CDN 短时限流（`mcdn.bilivideo.cn` 503），加重试能自己扛过去。

### 说明
- ffmpeg **没有内置进 exe**（保持 17.6MB 不膨胀）。
  想完全离线自足，把 `ffmpeg.exe` 放进 `launcher/` 目录再打包即可，`build_win.py` 会自动带上。
- 查找 ffmpeg 的顺序：**内置/同目录 → exe 旁边 → 本地缓存 → 系统 PATH**。

## v1.1 — 界面重做（用户反馈「太杂」）

**背景**：原界面把 yt-dlp 的所有原始格式全摊出来（分P、分CDN、音视频分离流……），一屏十几行，看不出该点哪个。

### 新增
- **按清晰度聚合**：一屏十几行原始格式 → 收成 **1080P / 720P / 480P / … / 仅音频** 几行。
  - 每档优先选「纯视频流（最高码率）+ 最佳音频流」，没有独立音轨时退回「自带音频的整段流」。
  - 显示编码（H.264 / H.265 / AAC…）、**预计文件大小**、是否「需合并」。
  - 大小 = 视频 + 音频相加；网站没给大小时按「码率 × 时长」估算并标 `≈`。
- **视频卡片**：封面缩略图 + 标题 + 作者 + 时长。
- 原始格式表折进「高级 · 排错用」，需要时还能用。

### 验证
拿真实链接实测：**15 条原始格式 → 5 条清晰度选项**；实际下载 360P 走通
「视频流 + 音频流分开下 → 自动合并」，产出合法 MP4，大小与预估一致。

## v0.2 — 重构成「自举启动器」

### 变更
- 从「一个 server.py + 一个 index.html」重构为**单目录分发**：
  `launch.py`（主程序）/ `build_win.py`（Windows 打包）/ `mux_fmp4.py`（鸿蒙合并器）/ `index.html`（界面）。
- 双击 / 运行后自动：检测系统 → 自检 yt-dlp → 选合并方式 → 起本地服务 → 开浏览器。
- **跨平台**：鸿蒙用自带的 Python 合并器绕过 ffmpeg；Windows / macOS / Linux 用 ffmpeg。
- 新增 `build_win.py`，用 PyInstaller 打成单文件 exe。

### 踩坑
- ⚠️ **Win11 ARM 上必须装 x86-64（amd64）版 Python**。
  装 ARM64 原生版会因 PyInstaller 缺 arm64 引导器而打包失败；x64 版在 ARM 上走模拟，标准引导器可用。
- 打包出的 exe 用 PE 头验证为 `Machine = 0x8664`（x64），班级 x64 电脑可正常运行。

## 待办 / 已知限制

- ❌ **不支持的平台**（引擎层面缺提取器，暂时无解）：
  **微信视频号**（含公众号视频）、**快手**、微视、咪咕视频、皮皮虾。
  视频号是微信封闭生态、内容加密，公开工具都拿不到 —— 只能请作者发原视频或手机录屏。
- 🟡 **多P视频 / 合集 / 播放列表**：目前一次下载一个；多P视频下的是你复制链接时的那个 P。
- 🟡 **「从浏览器直接读取登录信息」**：即 yt-dlp 的 `cookies-from-browser`。
  做出来老师就**完全不用手动复制 cookie**，是下一版最值得加的。
- 🟡 **YouTube 解析不稳定**：YouTube 近年加强限制（需要 PO token 等），部分视频解析不到格式。
- 🟡 **合并阶段没有细分进度条**：现在只显示「合并中…」，大文件时看着像卡住。
- 🟢 **未内置 ffmpeg**：首次运行需要联网下约 50MB（仅一次）；要完全离线可手动放进 `launcher/`。

## 环境备注

- 源码在鸿蒙电脑上开发和验证（HarmonyOS 7 / aarch64）。
