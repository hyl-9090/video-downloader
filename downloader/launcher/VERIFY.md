## 0. 前置：先确认你验的是最新版（最容易出错的一步）

工具的源码在 **F 盘共享目录**（鸿蒙主机侧路径 `/storage/Users/currentUser/F/2026 英语歌曲大赛MV/downloader/launcher/`，
VM 侧通常是 `F:\2026 英语歌曲大赛MV\downloader\launcher\` 或 `\\HwFs\HMOS_F\2026 英语歌曲大赛MV\downloader\launcher\`）。

⚠️ **关键**：如果 VM 里有一份**早些时候拷进来的旧拷贝**，验它等于白验。
请**先把 F 盘那份重新拷过来覆盖**，再开始。拷完先确认版本号：

```
findstr /C:"界面 v" index.html
```

**期望看到 `界面 v1.5`**。不是 v1.5 就先别往下走，说明拷的是旧版。

同时确认 `launch.py` 里有这几个新函数（存在即为对）：
`normalize_url`、`unsupported_hint`、`build_choices`、`normalize_cookie`、`find_ffmpeg`、`_prep_deps`

```
findstr /C:"def normalize_url" /C:"def unsupported_hint" /C:"def build_choices" /C:"def normalize_cookie" /C:"def find_ffmpeg" /C:"def _prep_deps" launch.py
```

## 3. 功能验证（重点）

### 3.1 正常解析
```
curl -X POST http://127.0.0.1:8932/parse -H "Content-Type: application/json" -d "{\"url\":\"BV1GJ411x7h7\"}"
```
**期望**：返回 JSON，`title` 非空，`choices` 有 **5 条**左右，形如
`1080P / 720P / 480P / 360P / 仅音频`，每条带 `filesize` 和 `merge` 字段。
（顺便验证：**只粘 BV 号**也能认出来。）

### 3.2 分享文案自动识别
```
curl -X POST http://127.0.0.1:8932/parse -H "Content-Type: application/json" -d "{\"url\":\"7.15 复制打开抖音，看看【某某】 https://www.bilibili.com/video/BV1GJ411x7h7 复制此链接\"}"
```
**期望**：和 3.1 一样能解析成功——说明程序从**一整段汉字文案**里把链接抠出来了。
（也应在界面上手工验证一次：把整段文案粘进输入框点「解析」。）

### 3.3 不支持的平台应被提前拦下
分别试这几条：
```
curl -X POST http://127.0.0.1:8932/parse -H "Content-Type: application/json" -d "{\"url\":\"https://channels.weixin.qq.com/web/pages/feed?x=1\"}"
curl -X POST http://127.0.0.1:8932/parse -H "Content-Type: application/json" -d "{\"url\":\"https://v.kuaishou.com/abcDEF\"}"
```
**期望**：都返回 `{"error": "…中文说明…", "friendly": true}`，
内容是**中文 + 替代办法**（视频号那条应说明"微信视频加密、公开工具都拿不到，建议让作者发原视频或录屏"）。
**不应该**返回英文的 `Unsupported URL`。

### 3.4 cookie 格式自动转换
**背景**：yt-dlp 只认严格的 Netscape 格式，F12 复制的那串原本会被拒绝。v1.4 起会自动转换。

```
curl -X POST http://127.0.0.1:8932/parse -H "Content-Type: application/json" -d "{\"url\":\"https://www.bilibili.com/video/BV1GJ411x7h7\",\"cookie\":\"SESSDATA=fakevalue%2C123; bili_jct=fakejct\"}"
```
**期望**：不报"cookie 格式不对"，能正常返回结果。
⚠️ **注意**：这里填的是**伪造的** cookie，所以返回的清晰度**可能比不带 cookie 时更少**（实测会从 1080P 掉到 480P）。
这是**网站的行为**，不是 bug。请用下面的**对照实验**确认这一点：

```
（不带 cookie）→ 记下清晰度档数
（带伪造 cookie）→ 记下清晰度档数
```
**期望**：带无效 cookie 的档数 **≤** 不带时的档数。请在报告里如实写出两组数字。

### 3.5 真下载（最关键）
界面上：解析 → 选 **360P** → 点「⬇ 开始下载」→ 等下完。

VM 是 Windows，会走 **ffmpeg 合并**路径（不是鸿蒙的内置合并器）。

**期望**：
- 进度依次出现 `[下载视频] …` → `[下载音频] …` → `[合并]`
- 出现 `✅ 完成: xxx.mp4`
- 文件是**能播放的完整视频**（有画面**也有声音**）
- 文件里应存到「下载」文件夹下的 **视频下载器** 子文件夹

请报告**文件大小**和**能否正常播放（含声音）**。

## 6. 「看着像失败、其实正常」的现象（避免误报）

| 现象 | 说明 |
|---|---|
| 首次运行卡着不动 | 在后台下 ffmpeg（约 50MB），页面顶部有 ⏳ 提示。**只下一次** |
| B站 下载报 503 / timeout | B站 CDN 短时限流。隔几分钟重试即可，不是代码问题（已实测：绕开本程序单独拉同一条流 7 秒就下完） |
| YouTube 解析出 0 个格式 | 已知情况，YouTube 近年加强了限制。界面会提示"没找到可下载的视频" |
| 带无效 cookie 后清晰度变少 | 网站行为（认不出会员就按未登录处理）。见 3.4 |
| 微信视频号 / 快手不能下 | **确实不支持**，这是预期结果，不是缺陷 |
| `__pycache__` 目录出现 | Python 自动生成的缓存，正常 |

## 7. 已知边界（不要当成缺陷来报）

- 平台那一栏的 ✅ 只验证到「**提取器存在 + 网址格式匹配**」这一层；**只有 B站做过真实下载验证**。
- 微信视频号（含公众号视频）、快手、微视、咪咕视频、皮皮虾：**引擎层面就没有对应提取器，做不了**。
- 音乐类（网易云 / QQ音乐 / 酷我）：提取器有，但多数需要登录或会员；**酷我只认 `kuwo.cn/yinyue/<数字>` 形式**。
- 一次只能下一个视频；多P视频下的是所复制链接的那一个 P。
